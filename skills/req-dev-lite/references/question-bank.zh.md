# 问题库（Question Bank）

可直接拿来用的拷问问句。

**三段式约定**（每个问句组必填）：
- **Recommended answer**：用户**应该**给出的回答形状（具体例子，不是抽象模式）
- **Why ask**：这条问句拦截哪种反模式 / 揭示什么真相
- **Push-back if**：用户答得不对路时，agent 该如何拉回

> 💡 设计意图：把"先给推荐答案 + 推理透明"从规则文字升级为问句的句法。agent 用问句时让用户**看到** Recommended，验证而非空想；用户跑偏时按 Push-back 拉回。

---

## 1. Mom Test 禁用问句（永远不要问）

> 这一节是**反向清单**，不是要问的问句，没有三段式。出现在 agent 自己的草稿里就立刻替换。

| 禁用问句 | 为什么禁用 | 替换为 |
|---|---|---|
| 「你会不会用这个功能？」 | 引导性回答，朋友为了不扫兴会说会 | 「你**上次**遇到这个问题是怎么处理的？」 |
| 「这个想法怎么样？」 | 开放式恭维征集器 | 「你**今天**怎么解决类似问题？花多少时间？」 |
| 「你觉得 X 重要吗？」 | 谁都会说重要 | 「**上一次** X 出问题，给你造成了什么具体损失？」 |
| 「你会为 X 付费吗？」 | 未来意图不可信，研究表明转化率 < 10% | 「你**现在**为类似的解决方案付了多少钱？」 |
| 「想象一下如果有 X……」 | 假设情境产生 confabulation（事后编造） | 「**最近一次**类似场景是什么时候？走一遍。」 |
| 「**以后**会不会……」 | 同上，未来时禁用 | 「**过去三个月**这种情况出现过几次？」 |
| 「这个功能有用吗？」 | 几乎总会得到「有用」 | 「**没有这个功能时**你怎么应对的？」 |
| 「你**应该**……？」 | 引导用户给"正确答案" | 「你**实际上**是怎么做的？」 |

> 💡 **检测原则**：如果一个问句让人想"礼貌地说有用"或"出于支持给个肯定答案"，它就是禁用问句。

## 2. Mom Test 强制问句模板

### 2.1 时间锚定（永远问过去，不问未来）

**问句**：
- 「**上次** [行为] 是什么时候？」
- 「**最近一次** [问题] 发生是什么时候？」
- 「**过去 [时间窗口]** 你做了 [行为] 几次？」
- 「**今天上午/昨天** 你是怎么 [行为] 的？」

**Recommended answer**：具体时间锚 + 具体动作。
> 例：「上周三下午，我用 Excel 手工对账了 200 行订单，花了 90 分钟。」

**Why ask**：拦截"未来时陷阱"。过去具体行为是事实，未来意图是想象——事实可挖，想象不可靠。

**Push-back if**：
- 用户答「以后会……」/「通常会……」/「我们一般会……」 → 拉回：「那**最近一次**是什么时候？走一遍那次。」
- 用户答「经常」/「很多次」 → 量化：「过去 30 天发生过几次？」
- 用户答模糊行为（如「我处理了一下」） → 走 narrative：「具体那次你点了什么、看到了什么、然后做了什么？」

---

### 2.2 走一遍（force narrative）

**问句**：
- 「**从最开始**走一遍那次的步骤。」
- 「**一步一步**讲，你点了什么、看到了什么、然后做了什么？」
- 「那之后**接下来**发生了什么？」
- 「**在你做 X 之前**你做了什么？」

**Recommended answer**：有序步骤 + 每步看到的具体界面/数据/反馈。
> 例：「先打开 Salesforce → 切到 Opportunities → 筛 Q4 closed-won → 导出 CSV → 在 Excel 用 VLOOKUP 拼字段 → 邮件发给 finance@」

**Why ask**：narrative 暴露**隐藏步骤、隐藏决策、隐藏 workaround**。"描述一下你的流程"会得到抽象总结；"走一遍上次"会得到所有细节。

**Push-back if**：
- 用户给抽象描述（「就是先查数据再处理」） → 「**那次**你查了什么数据？用什么工具查的？」
- 用户跳步（「然后就好了」） → 「等等，从 X 到 Y 之间还有什么？是手工的还是系统自动的？」
- 用户说不记得 → 「最近一次还能记得的是哪次？」或「现在能复现一遍给我看吗？」

---

### 2.3 现状揭示（揭穿"需要"的真伪）

**问句**：
- 「**今天**你怎么解决这个问题？」
- 「**没有这个功能时**你用什么 workaround？」
- 「这事**至今没修**是为什么？」
- 「你**已经尝试过**什么办法？」

**Recommended answer**：具体的 workaround 描述 + 代价 + 该 workaround 的局限。
> 例：「我现在用 Google Sheets + IMPORTRANGE 手动同步，每周一早上花 20 分钟，但行数超过 5000 就会报错。」

**Why ask**：真实痛点的标志是用户**已经在 hack 解决方案**。没有 workaround = 痛得不够 = 可能是 nice-to-have 不是 must-have。

**Push-back if**：
- 用户答「没办法，就那样」 → 「真的什么都没做吗？还是说做了但不愿承认那是 workaround？给我具体例子。」
- 用户答「我们计划……」 → 拉回："不是计划，是**现在**怎么应付的？"
- 用户答「这个我们打算用 AI 解决」 → 5 Whys 拦截器启动（见 §4）

---

### 2.4 量化痛苦

**问句**：
- 「**上一次** [问题] 让你损失了多少 [时间/钱/客户/订单]？」
- 「这事每周/每月发生几次？」
- 「不修这事**最糟糕的情况**会怎样？」
- 「为了应对这事你每周花多少时间？」

**Recommended answer**：数字 + 单位 + 时间窗口。
> 例：「Q3 因为对账延迟丢了 3 个 enterprise 客户的续费，单子加起来 $480K ARR。每周对账平均要花团队 12 小时。」

**Why ask**：未量化的痛苦在排期会议上会被砍掉。**量化是需求活下去的护身符**。同时，量化暴露真假痛——真痛能给出数字，假痛只能给"很多"。

**Push-back if**：
- 用户答「很多」/「不少」 → 「**具体多少**？给我一个数字范围也行。」
- 用户答「不好估」 → 「上次这事发生具体损失了什么？光那次的代价能不能算出来？」
- 用户答「没法量化，是体验问题」 → 拆分：「体验差导致**用户做了什么**？流失？工单？投诉？任一一个都可量化。」

---

### 2.5 揭示阻碍（为什么至今没修）

**问句**：
- 「这事**早就该修了**——为什么没修？」
- 「之前**尝试过**修这事吗？为什么没成？」
- 「修这事**最大的阻碍**是什么？」

**Recommended answer**：具体的阻碍源（人/技术/优先级/组织/合规），最好附之前的失败尝试。
> 例：「2 年前 Backend 团队提过用 Kafka 重写，但 DevOps 没人懂运维 Kafka，且当时 PM 把 dashboard rework 排在前面，后来人换了就不了了之。」

**Why ask**：揭示**真实优先级、组织阻力、技术依赖**。"早该修"但"一直没修"，背后一定有原因——这个原因往往就是真实约束，会影响 PRD 的可行性。

**Push-back if**：
- 用户答「没什么特别原因」 → 「那为什么过去 N 个季度都没排上 sprint？谁在决定优先级？」
- 用户答「之前没人想过」 → 反直觉信号：「真的？这种痛 N 年没人提过吗？查一下 issue tracker / Slack 历史。」（这通常意味着用户不是真痛主）
- 用户答「就是没人有空」 → 「这事比哪些更不重要？列出排在它前面的 3 件事。」

## 3. Impact Mapping 开场问句

按这个顺序问，**不要跳步**。Why 和 Who 没钉死前禁止讨论 What。

### 3.1 Why（业务目标）

**问句**：
- 「这个需求服务**哪个业务目标**？是 OKR 里哪一条的子项？」
- 「成功长什么样？**用什么指标量化**？基线和目标值分别是多少？」
- 「如果**这个目标不存在**，这需求还需要做吗？」

**Recommended answer**：明确的 OKR/北极星指标子项 + 基线数字 + 目标数字 + 截止时间。
> 例：「服务 Q2 OKR 'reduce customer onboarding time by 50%'。当前 onboarding 中位数 14 天，目标 ≤7 天，2026 Q2 末验收。」

**Why ask**：Why 是 PRD 的根。没钉死 Why 就讨论 What，会做出"不知道为什么要做"的功能——上线后没人会用，retrospective 时说不清成功标准。

**Push-back if**：
- 用户答「就是要让产品更好用」/「提升用户体验」 → "更好用"不是 Why，是 weasel word：「**哪个指标**会因为这个变好？基线和目标？」
- 用户答「老板说要做」 → 「老板想撬动哪个业务结果？目标值是多少？」
- 用户答「竞品都有了」 → 「我们不做这事，竞品**具体**会抢走什么——多少用户？多少 ARR？」

### 3.2 Who（参与者）

**问句**：
- 「**谁**的行为必须改变才算成功？（具体到岗位/角色，不是"用户"）」
- 「这些人**之外还有谁**会被影响？是好的影响还是坏的？」
- 「**谁可能反对**这个变化？」

**Recommended answer**：具体岗位/角色 + 当前人数 + 该岗位的典型一天。
> 例：「Mid-market AE（约 40 人），每周开 15-20 个 demo call。变化点：从 demo 后手工 follow-up 邮件 → 自动化 follow-up，AE 只需 review/批准。」

**Why ask**："用户"是 weasel word。不到岗位级，PRD 的 user story 就写不具体——验收时不知道谁该用，不知道行为是否真改变。

**Push-back if**：
- 用户答「我们的用户」/「客户」 → 「**哪类客户**？哪些岗位？enterprise PM 还是 SMB founder？」
- 用户答「所有人」 → 「不可能。哪类**首先**改变行为？其他类是 follow-on 还是无关？」
- 用户没考虑反对者 → 「如果这个上线**伤害**了谁——客服？销售？谁会拍桌子？」

### 3.3 How（行为改变）

**问句**：
- 「这些人**当前的行为**是什么样？」
- 「**改变后**他们的行为应该是什么样？（X 行为 → Y 行为）」
- 「**怎么知道**他们的行为真的改了？（可观察的信号）」

**Recommended answer**：当前 X 行为（动词 + 频率 + 工具）→ 目标 Y 行为（动词 + 频率 + 工具）+ 可观察信号。
> 例：「当前：每周一手工跑 SQL 拉数据 30 分钟。目标：每周一打开 dashboard 0 分钟。信号：dashboard 每周 Mon 9–11am UV 增长 ≥3x。」

**Why ask**：行为改变是 outcome 的唯一证据。如果行为没变，PRD 即使上线也没产生价值。**信号必须可观察**，否则验收吵不清。

**Push-back if**：
- 用户答「他们会更喜欢这个产品」 → "喜欢"不可观察：「**做什么动作**能证明他们更喜欢？登录频率？分享率？」
- 用户答「他们会用新功能」 → 「**比起**继续用旧 workaround，他们**为什么**会切？切的信号是什么？」
- 用户答行为太大（如「他们会变成 power user」） → 拆解：「power user 的**第一个**行为是什么？最小可观察单元。」

### 3.4 What（交付物）

**问句**：
- 「**最小**我们能造什么来撬动这个行为改变？」
- 「除了软件，还可以**怎么撬动**这个行为改变？（培训？流程？激励？）」

**Recommended answer**：最小 deliverable 描述 + 撬动机制 + 为什么这个比"造更大的东西"高效。
> 例：「最小：在现有 dashboard 加一个 'auto-refresh on Monday 8am' 选项。撬动：每周一打开 = 0 摩擦看数据。理由：不需要新页面、不需要培训，行为切换成本接近 0。」

**Why ask**：验证软件是不是真的最优解。很多需求拆开看，其实 PSA（流程/培训/激励）比软件改动更高效。

**Push-back if**：
- 用户答「做一个完整新系统」 → 「能不能**先做半个**测一下？哪一半最关键？」
- 用户答「这必须软件做」 → 「**为什么不能**用培训/激励/流程？给三个理由，每个反驳一下。」
- 用户答「最少要 A+B+C 才能撬动」 → 「**只做 A** 行为改不改？信号是什么？」

## 4. 5 Whys 拦截器（触发于"我要 X 方案"）

**触发条件**：用户提具体技术/工具/实现方案（「我要用 Redis」「加一个开关」「做个仪表盘」「用 MongoDB」「上 AI」）。

**问句序列**（用户每答一次，立刻问下一句，不允许跳过）：

1. 「为什么你想用 [方案 X]？」
2. 「为什么 [上一个答案] 这件事重要？」
3. 「为什么 [上一个答案] 现在重要、不能延后？」
4. 「**谁**会因为做不到 [上一个答案] 而受影响？影响多严重？」
5. 「**底层 outcome** 是什么？用这个句式：**『最小化/最大化 [动词][对象][约束]』**」

**Recommended answer**（第 5 步给出的）：Ulwick 句式的具体陈述。
> 例：「**最小化** [客户从 demo 到首次价值实现的时间] [约束在 7 天内]。」

**Why ask**：O'Hara 2025（TechRxiv preprint）报告 5 Whys 拦截器在 6 个行业反模式上 100% 检出"伪装成需求的方案"（小样本支持性证据）。挖到底层 outcome 前，方案进 PRD 等于做错事。

**Push-back if**：
- 用户在第 1–4 步答「就是想用」/「直觉觉得好」/「同行都在用」 → 「**具体哪个业务结果**会因为没用它而受损？」
- 用户卡在第 5 步答不出 Ulwick 句式 → 给三个候选模板让用户选：「是要最小化某个时间？最大化某个转化？降低某个错误率？」
- 用户答的 outcome 实际是另一个方案（如"我们要快"） → 「**多快**？以哪个动作的延迟为基准？」

**挖到底层 outcome 后的处理**：把 outcome 记入桶 B（带基线 + 目标 + 截止），原方案 X 降级为 PRD 的 Implementation Decisions 候选之一（不是 Requirements）。

## 5. Cockburn Extensions 枚举问句

对每条主流程的**每一步**问以下问题。不允许只问 happy path。

**问句模板**：
- 「**Step N 失败**会怎样？用户看到什么？」
- 「**Step N 超时**怎么办？等多久？提示什么？」
- 「**Step N 并发冲突**怎么办？」（多个用户同时操作）
- 「**Step N 部分成功**怎么办？」（事务一半提交）
- 「**Step N 网络断**怎么办？」
- 「**Step N 用户取消**怎么办？已完成的部分回滚吗？」

**Recommended answer**：明确的 fallback 行为 + 用户可见反馈 + 数据状态。
> 例：「Step 3 (提交订单) 超时：5 秒未响应 → 前端显示『仍在处理，请勿重复提交』；后端幂等检查避免重复扣款；超过 30 秒仍未响应 → 落"pending review"队列由人工跟进。」

**Why ask**：多数 PRD 上线翻车都是因为只写了 happy path。Cockburn extensions 是验收前最便宜的保险。

**Push-back if**：
- 用户答「应该不会发生」 → 「不修这个分支**最糟糕**会怎样？如果接受这个最坏后果，写进 PRD 的 Known Risks。否则继续讨论。」
- 用户答「正常情况下没事」 → "正常"是 weasel word：「不正常时呢？给出具体行为。」
- 用户答「跳过这种 case」 → 必须落字：「PRD 写明'本 PRD 不处理 Step N 失败，由 Issue #NNN 跟进'。」

## 6. 7 标签审查问句（终审）

每条 user story **过一遍下表**。命中即处理。

| 标签 | 审查问句 | Recommended pass shape | 命中处理（Push-back） |
|---|---|---|---|
| `[Contradiction]` | 这条 story 和已写的哪条**冲突**？ | 无冲突；或冲突已用 ADR 显式裁决 | 让用户**选边**，留 ADR |
| `[Gap]` | 用户走完这条流程后下一步去哪？有**断点**吗？ | 完整状态图，无断点 | 补中间状态或开 issue 跟进 |
| `[Fallacy]` | "因为 A 所以 B" 的推理**真的成立**吗？ | 因果有证据（数据/案例/共识） | 让用户给证据，否则降级为假设 |
| `[Redundancy]` | 这条和已有哪条**说的是同一件事**？ | 无重复 | 合并或砍掉一条 |
| `[Dangling]` | 这条提到的实体/角色/数据**谁拥有/谁产生**？ | owner 明确 | 补 owner，无 owner 不允许进 PRD |
| `[Overreach]` | 这条**超出了**阶段 1 商定的 Why 吗？ | 在 Why 范围内 | 砍或开新 PRD |
| `[Unowned]` | 未决事项**谁负责跟进、什么时候给答案**？ | 有 owner + deadline | 补 owner + deadline，TBD 必须 24h 内补全否则砍 |

**Why ask**：7 标签是 PRD 终审最后一道闸门。每条 user story 至少跑一遍，命中任一标签 → 阶段 5 触发"回炉"或"PASS-WITH-OPEN-ITEMS"判断（见 SKILL.md 阶段 5）。

## 7. 领域校准问句（grill-with-docs 子集）

**问句**：
- 「你说 [术语]，**glossary 里定义是 X**——你指的是 X 还是另一个含义？」
- 「[术语 A] 和 [术语 B] **是同一个东西吗**？还是有区别？」
- 「编一个**极端场景**：[场景]——这种情况下系统该怎么反应？」
- 「代码里**这部分写的是 X**，你刚才说是 Y——哪个对？」
- 「这个**关系是 1:1、1:N、还是 M:N**？给我一个真实例子。」

**Recommended answer**：术语精确到字段/表/类；关系精确到基数；冲突时显式裁决并 inline 更新 CONTEXT.md。
> 例：「'订单'指 `orders` 表的 row（不含子表 `order_items`）。一个用户 1:N 订单。极端场景：用户删号时已下单未发货的，订单状态变 `orphaned`，财务月结时人工对账。」

**Why ask**：术语漂移是 PRD 上线后 bug 的最大单一来源。"账户/订单/取消"这些词在不同人嘴里指不同对象。

**Push-back if**：
- 用户使用 glossary 没收的术语 → 「这个词项目里没定义。**给一个真实例子**让我能写进 glossary。」
- 用户和代码语义不一致 → 「代码 X，你说 Y——选一个并 inline 更新 CONTEXT.md；如果是重大变更，开 ADR。」
- 关系答模糊（「大概是 1 对多」） → 「**给一个具体例子证明 1:N，再给一个反例证明不是 M:N。**」
