# 需求开发方法注释

这里列出 req-dev 用到的所有方法，**5 个必跑核心** + **6 个按信号触发的可选模块**。每个方法都有：一句话定义 / 适用场景 / 在 skill 里负责什么 / 跳过条件 / 我的注释。

---

## 核心方法（必跑）

### 1. The Mom Test（Rob Fitzpatrick, 2013）

**一句话**：好问题是「你妈也不会对你撒谎的问题」——问过去具体行为，不问对未来/假设的看法。

**适用**：每一次需求访谈。

**在 skill 里**：阶段 2 的拷问纪律层。禁用引导性问句，强制过去时具体行为问句。

**跳过条件**：永远不跳过。

**我的注释**：这是单条投资回报率最高的方法。书原文里 Fitzpatrick 反复举例：创业者去问「你会不会用我这个 app？」朋友们都说会，结果上线无人下载——因为朋友在保护友谊，不在评估产品。换成「上次你遇到这个问题怎么处理的？」答案立刻具体且诚实。

**核心三规则**：
1. 谈他们的生活，不谈你的想法
2. 问过去具体行为，不问未来意图或观点
3. 少说多听

**红旗**：用户用「应该」「可能」「会」「以后」造句——基本都在敷衍。立刻拉回过去时。

---

### 2. Impact Mapping（Gojko Adzic, 2012）

**一句话**：四层思维导图——Why（业务目标）→ Who（参与者）→ How（行为改变）→ What（交付物）。

**适用**：每个 PRD 开场。

**在 skill 里**：阶段 1 开场四问。Why+Who 没钉死禁止讨论 What。

**跳过条件**：纯合规/审计需求（Why 就是「通过审计」，没什么好挖的）。

**我的注释**：这是反「feature factory」最有效的工具。多数糟糕 PRD 的特征是「直接从 What 开始」（「我们要做一个仪表盘」），从不回答「这服务什么业务目标」。Adzic 的核心洞察是：**What 是最不重要的——80% 的初始 What 会被替换，但 Why/Who/How 极少变。**

**实操**：把对话拽回 Why 的次数会让用户不耐烦，但这就是技能价值所在。耐心点。

---

### 3. 5 Whys（Toyoda Sakichi → Taiichi Ohno，丰田生产系统）

**一句话**：连问 5 层 why，挖到根因/底层 outcome。

**适用**：用户提出具体方案/技术/实现的瞬间。

**在 skill 里**：阶段 2.5 的解决方案拦截器。

**跳过条件**：纯 bug 修复（根因显而易见）；线性简单问题。

**我的注释**：Toyoda 的原始场景是车间机器停机：「为什么停机？保险丝烧了。为什么烧？过载。为什么过载？轴承不润滑。为什么不润滑？油泵磨损。为什么磨损？没装过滤器。」5 层后从「换保险丝」变成「装过滤器」，根本性的解。

**注意 Minoura 的批评**：5 Whys 在复杂系统里可能产生「假根因」幻觉（你认为挖到底，但其实是单条因果链上的可达点之一）。所以在 skill 里我用 O'Hara 2025（TechRxiv preprint）的做法：**LLM 负责拷问对话，验证由确定性规则做（Volere QG）**——5 Whys 不是终点，是把方案降级为「候选实现」的拐杖。

**Ulwick 句式**（5 Whys 落点）：把根因写成「最小化 / 最大化 [动词][对象][约束]」的 outcome 语句。例：「最小化客户从下单到收到发货通知的等待时间，在促销日峰值并发下不退化」。

---

### 4. Specification by Example / Gherkin（Gojko Adzic）

**一句话**：每条需求配至少一个 Given-When-Then 具体例子，含真实数值。

**适用**：所有验收标准。

**在 skill 里**：阶段 4 的硬性产出格式。

**跳过条件**：纯视觉/审美需求（「主色调要稳重」这种）。

**我的注释**：Adzic 的核心论断：**写不出失败的具体例子，需求就不成熟。** 抽象 AC 是 ambiguity 的温床。例：「应该正确处理金额」——什么叫正确？大于 0？小于余额？精度几位？要不要支持负数（退款）？换成 Gherkin：

```gherkin
Given 用户余额为 ¥100.00
When 提现金额 ¥150.00
Then 显示"余额不足"，余额仍为 ¥100.00，不产生提现记录
```

写出第二个例子时，矛盾自然暴露——「那如果是分期呢？」「那如果有信用额度呢？」——这些都是隐藏需求，提前暴露便宜。

**SBE 之于 BDD**：BDD 是工具（Cucumber 等），SBE 是哲学（用例子驱动需求成熟）。我们要的是 SBE 哲学，Gherkin 只是它的表达形式。不强制项目装 Cucumber。

---

### 5. Cockburn Use Case Extensions（Alistair Cockburn, 1990s）

**一句话**：每条主流程必须枚举「步骤 N 失败/分支会怎样」。

**适用**：所有有交互流程的需求。

**在 skill 里**：阶段 4.5 完整性闸门。

**跳过条件**：纯计算/转换类需求（无外部交互）。

**我的注释**：Cockburn 的 fully dressed 用例模板有 12 个段，但灵魂段是 Extensions（扩展）。绝大多数 PRD 翻车不是 happy path 没写好，是 happy path 之外的分支漏写。Extensions 强制你逐步反问「step N 失败会怎样？」

**实操模板**：
```
主流程：
  1. 用户点击「提现」
  2. 系统校验余额
  3. 系统冻结资金
  4. 系统调用银行接口
  5. 系统记录流水
  6. 用户看到「提现已申请」

Extensions:
  2a. 余额不足 → [具体行为]
  3a. 冻结失败（并发） → [具体行为]
  4a. 银行接口超时 → [具体行为，重试策略]
  4b. 银行接口拒绝（风控） → [具体行为]
  5a. 流水记录写库失败 → [具体行为，回滚策略]
```

每条 a/b/c 都是一个潜在生产 bug 的提前曝光点。

## 辅助方法（必跑，但更轻）

### 6. INVEST（Bill Wake, 2003）

**一句话**：user story 六字检查——Independent / Negotiable / Valuable / Estimable / Small / Testable。

**适用**：每条 user story 离开拷问会话前。

**在 skill 里**：阶段 4 的 30 秒过审。

**我的注释**：太常用以至于看起来 trivial，但每条不过的 story 都是 sprint 灾难。Small 这条最常被忽略——「一句话需求」往往隐藏 3 个 sprint 的工作。

---

### 7. Volere Quality Gateway（Suzanne & James Robertson）

**一句话**：每条需求必须过四问——可测试、可追溯、无方案语言、无 weasel word。

**适用**：阶段 5 终审。

**在 skill 里**：硬性闸门，不过则回炉。

**我的注释**：Volere 完整有 30 个段，太重，不全套引入。只取 Quality Gateway 这个核心机制。「weasel word」清单：user-friendly / fast / quick / appropriate / reasonable / flexible / robust / scalable / simple / intuitive——所有这类形容词都是需求剧场。

---

## 可选方法（按上下文信号触发）

### 8. Event Storming（Alberto Brandolini）

**触发信号**：用户提到「微服务」「DDD」「领域复杂」「业务流程长」。

**在 skill 里**：插入阶段 3，让用户按时间线列出 domain events（过去时动词，「订单已支付」「库存已扣减」），再补 actor / command / aggregate。

**注释**：传统 Event Storming 是工作坊（橙色便利贴 + 大白墙），在 LLM 对话里要降维成「按时间顺序逐个列出事件」。Brandolini 的核心问句：「这个事件之前发生了什么？之后发生了什么？」

---

### 9. JTBD / ODI（Christensen 提出 / Ulwick 操作化）

**触发信号**：greenfield 项目，「我们要做一个全新的 X」「C 端用户场景」。

**在 skill 里**：阶段 1 之后插入 outcome 收集——Ulwick 句式「最小化/最大化 [动词][对象][约束]」。

**注释**：ODI 完整做法是定量收集 50-150 个 outcome 然后调研排序，这在 LLM 对话里做不了。但**句式**可以拿来用——它强制把需求写成「可测量的结果」而非「功能」。「让用户能预约」是功能；「最小化从产生预约意图到完成预约确认的等待时间」是 outcome。

---

### 10. KAOS 目标树 / 反目标（Obstacle Analysis, van Lamsweerde）

**触发信号**：多目标冲突、安全/合规敏感、有「不希望发生的事」清单。

**在 skill 里**：把 Why 拆成 AND/OR 子目标，同时列 obstacles（如果 X 发生，目标失败）。

**注释**：obstacles 这个概念被 PM 们严重低估。多数 PRD 列了「成功标准」，从不列「失败条件」。补一句「如果发生 X，整个 feature 都失败」立刻让风险显形。

---

### 11. Continuous Discovery / Opportunity Solution Tree（Teresa Torres）

**触发信号**：已上线产品迭代、有用户行为数据、有定期访谈节奏。

**在 skill 里**：阶段 1 之后强制建 OST 结构——Outcome → Opportunity → Solution → Assumption Test。

**注释**：OST 的硬约束是**任何 Solution 都必须挂在 Opportunity 下，Opportunity 又必须挂在 Outcome 下**。漂浮的 Solution 直接拒收。这和我们的「三桶规则」呼应——孤儿 Solution 进桶 C。

---

### 12. Critical Decision Method（Klein / Hoffman）

**触发信号**：用户是 SRE / 操作员 / 交易员 / 专家用户；要挖隐性知识。

**在 skill 里**：让用户挑一个近期具体的难决策事件，时间线重放——什么时候你注意到不对？考虑了哪些选项？为什么选了这个？什么样的信息会让你改变决策？

**注释**：访谈专家时直接问「你怎么决策？」得到的全是事后合理化。重放事件能挖出隐性 cue 和判断启发——这些是 happy path 描述永远不会出现的内容。

---

## 我没纳入的方法（避免方法论堆砌）

以下方法**没**作为可选模块，原因记在这里以备未来追溯：

- **i\* 框架**：和 KAOS 高度重叠，KAOS 已覆盖目标 + 反目标这部分。
- **User Story Mapping**：是规划/排期工具，本 skill 关注单需求拷问，超出范围。
- **MoSCoW / RICE**：优先级排序工具，应该在 PRD 落地后由 PO 操作，不在拷问阶段。
- **IEEE 830 SRS 完整模板**：太重，关键部分（功能性/非功能性区分、外部接口、约束）已通过 to-prd + Volere QG 间接覆盖。
- **Lean UX / Design Sprint**：是流程框架，不是单次拷问技术。

---

## 「越多越好」的边界

用户偏好「方法用越多越好」——这里的「越多」指**触发信号匹配时启用越多**，而不是**每次都全跑**。机械跑 11 个方法会让单次会话从 30 分钟膨胀到 3 小时，且大部分产出冗余。

正确姿势：
- 核心 5 个永远跑
- 辅助 2 个永远跑（INVEST + Volere QG）
- 可选 5 个**只在触发信号出现时**启用

每次会话开始前，agent 应该先用 1-2 分钟评估上下文，决定启用哪些可选模块，并明确告诉用户：「本次启用方法清单：XXX。理由：YYY」。
